# 设计说明

## 1. 现状：版本协商已经存在，只是每次都要回源

`usr-backend` 的课表接口（`router/client/getSchedule.go`）下发的版本串是复合串：

```
version = <dataVersion>:<weekNumber>[:<boundary>]
```

- `dataVersion`：作用域内所有会影响响应的时间戳的最大值（课表/作息/科目/客户端配置的
  `UpdatedAt`、显式版本行、命中的自动任务记录、倒数日记录）。
- `weekNumber`：当前周次，影响多周轮换课表的解析结果。
- `boundary`：自动任务（单日/日期范围/cron）下一次状态翻转的绝对时刻；没有后续变化点时省略。

客户端把整个串原样回传（`?version=...`），源站重新查库算一遍，三个分量都相同就回 304。

问题在于：**为了回一个 304，源站仍旧被调用一次、仍旧查了五张表**。课表很少变化，这部分是纯浪费。

## 2. 数据模型

### 键

| 用途 | 形式 | 说明 |
|---|---|---|
| 班级条目 | `s1.<host>.<base64url(班级路径)>` | 一个班级一条 |
| 世代 | `g1.<host>` | 一个域名一条 |

键里带 hostname 不是装饰：**namespace 由 Host 推导**（usr-backend 的
`middleware.ParseHostToNamespace`，`aaa-do.getastra.cn` → `cn/getastra/aaa-do`），
所以每个租户子域都是一套独立数据。同一个班级路径在不同子域下必须落到不同的键上，
反过来同一个子域的世代键也必须只失效它自己——这也是写请求按 host 推进世代的原因。

`base64url` 是对 UTF-8 字节的编码（字母表 `A-Za-z0-9-_`，无填充）。
班级路径必须编码，因为 ESA 边缘 KV 的键**拒绝非 ASCII**（实测：键 `中文键` 返回
`InvalidKey.Malformed`，空格返回 `InvalidParameters`，`.` 与 `_` 可用）。

### 值

```json
{ "v": "<版本串>", "e": 1758384000, "g": "<写入时的世代>" }
```

ESA 边缘 KV **没有 TTL 能力**（`EdgeKV` 只有 `get` / `put` / `delete`），
所以过期时刻 `e` 必须存在值里，由读取方自己比较。

## 3. 请求流程

### 读（`GET /:school/:grade/:class?version=...`）

1. 路径不是三段班级路径 → `fetch(request)` 透传。
2. 带 `Origin` 请求头（浏览器跨域）→ 透传。合成的 304 带不回源站的 CORS 响应头，
   浏览器会把它当成网络错误，所以这条路径不参与缓存。
3. 没有 `version` 参数 → 透传。
4. 读 `s1.*` 与 `g1.*`。命中条件（全部满足）才直接回 304：
   - `entry.v` 与客户端版本一致；
   - `entry.e` 尚未到期；
   - `entry.g` 与当前世代一致。
5. 否则**原样**回源（带着客户端的 `version`）：
   - 源站 200 → 从 `X-Astra-Schedule-Version` / `X-Astra-Schedule-Expire` 取元信息写 KV；
   - 源站 304 → 版本就是客户端带回的版本，从 `X-Astra-Schedule-Expire` 取过期时刻写 KV；
   - 源站没给头（5xx、老版本后端、别的接口）→ 不写 KV，响应原样返回。

第 5 步刻意保留 `version` 参数：源站自己的 304 快路径照旧生效（不需要序列化响应体），
边缘又不需要为了拿元信息多打一次源站。

### 写

GET 之外一律 `fetch(request)` 透传，但只有**会改变数据的方法**（`PUT` / `POST` / `PATCH` / `DELETE`）
返回 2xx 时才把 `g1.<host>` 换成一个新值。

这里必须用白名单而不是「非 GET/HEAD 就失效」：浏览器的跨域预检用的是 `OPTIONS`，
源站会对它回 2xx，按后者处理会让**每一次预检都把该域名下所有班级的缓存打掉**。
同理，键里的 host 取 `url.hostname` 而不是 `url.host`——后者会带上非默认端口，
而冒号不是边缘 KV 允许的键字符。

## 4. 为什么用「世代键」而不是逐个删键

issue 原本设想「边缘识别 PUT → 用源站返回的新版本更新 KV」。两个问题：

1. 源站要额外把新版本元信息塞进写响应里，每个写接口都得改。
2. **失效范围不够**。`/web/autorun/*`、`/web/countdown` 是全局作用域的写入，一次影响多个班级，
   而边缘 KV 只有 `get` / `put` / `delete`，没有前缀枚举，边缘无法知道该删哪些班级的键。

世代键把「失效」变成一个键的写入：**任意写请求都能一次性让该域名下所有班级的缓存失效**，
代价是每次班级 GET 多读一个键。

## 5. 过期时刻怎么算

源站计算 `X-Astra-Schedule-Expire`（绝对 Unix 秒）：

```
expire = min( boundary（若在 now 之后）, 下一个本地零点 )
```

零点这一项不能省。响应里的 `daily_class` 是按「今天」应用自动任务规则后展开的 7 天数组，
**午夜内容就会变**；周次与多周轮换课表也在周一变化，而周一同样是零点。
原来这三个分量是源站每次重新比较的，挪到边缘之后，边缘必须自己知道这个边界，
否则会在午夜之后继续用前一天的版本把客户端锁在旧课表上。

`boundary` 已经覆盖了「自动任务条件翻转」；数据本身被改动时 `dataVersion` 变化，
版本串不同，边缘自然回源。

## 6. ESA 平台限制（在真实账号上实测）

| 项 | 实测结果 | 对设计的影响 |
|---|---|---|
| 边缘 KV 键字符集 | 非 ASCII 拒绝（`InvalidKey.Malformed`）、空格拒绝；文档写明「不能包含空格、反斜杠 `/`」 | 班级路径必须 base64url 编码 |
| 边缘 KV TTL | **OpenAPI** 的 `PutKv` 有 `--Expiration` / `--ExpirationTtl`；但**边缘运行时的 `EdgeKV` 类**只有 `get`/`put`/`delete` | 边缘写不了 TTL，过期时刻只能存在值里 |
| 边缘 KV 一致性 | 文档：最终一致，一般几秒到十几秒，**最迟 300 秒**同步到全球节点 | 主动失效不是即时的，见第 7 节 |
| 边缘 KV 容量 | 单键 ≤512 字节，单值 ≤1.8 MB，单空间 1 GB，账号 10 GB | 键长约 40–80 字节，值约 60 字节，远低于上限 |
| 键值对数量 | `astra` 空间当前为空，配额 10 个空间 | 无需新建空间 |

## 7. 已知风险

### 7.1 最终一致带来的有界陈旧窗口

KV 写入最迟 300 秒同步到全球节点。也就是说：管理端改完课表之后，某些边缘节点在**最长约 5 分钟**
内仍可能拿着旧世代/旧条目直接回 304。这是方案本身的固有代价，不是实现缺陷。

缓解：源站下发的 `expire` 本身就是上界，配合客户端自身的刷新时机（进入下一个日程、启动、
失败重试），最坏情况是「改动生效延迟增加几分钟」。

**这个窗口为什么可以接受**：SaaS 是 serverless 模式，WebSocket 被禁用，客户端实际只在
「启动 / 进入下一个日程 / 失败重试」时拉取——其中最主要的是**进入下一个日程**，粒度就是一节课
（几十分钟）。客户端自身的刷新节奏本来就在分钟级，再叠加一个最长 5 分钟的窗口，对
「改完课表多久看到」的影响有限。这个方案真正的价值不是把生效延迟压到秒级，而是
**削峰与降低源站负载**：同一时刻大量班级开始上课会同时发起拉取，边缘 304 把这些请求
全部挡在源站之外。

如果这个窗口确实不可接受，唯一的替代是放弃边缘 304、回到每次回源，或者改用 ESA 缓存规则 +
`PurgeCaches` 主动刷新（purge 同样是异步的）。

### 7.2 边缘函数配额是账号级共享的

账号当前是**免费模式**（函数数上限 20，付费模式是 100）。免费模式限制
**每账号每天 10 万次函数请求**，超了直接返回 503。函数路由一旦挂到 `class.getastra.cn/*`，
该域名**所有**请求都会进函数并计数，包含天气接口、`/web/*` 和写请求。

站点近 7 天总请求量约 3.5 万（每天约 7 千–1.2 万），离 10 万还有量级余量，
但需要注意：**配额是账号级共享的**，超限会让 `docs-site`、两个 dashboard、`reg-go`
的函数一起 503。

### 7.3 收益主要是延迟，不是钱

付费模式下边缘函数 5 元/百万次。省下来的是 FC 调用与五张表的查询，绝对金额很小。
真正的收益是边缘 304 省掉一次回源往返 + 一次数据库读取，以及源站在高峰期少处理大量只读请求。

## 8. 降级与安全边界

- 缓存链路**任何**异常都降级为 `fetch(request)`：KV 构造失败、读失败、写失败、值解析失败、
  版本串格式不认识、过期字段非法，全部按 miss 处理。
- 版本串写入前按 `^[0-9A-Za-z:._-]{1,128}$` 校验，避免异常响应把任意内容灌进 KV。
- 合成的 304 不参与 CORS 路径，避免把浏览器的跨域请求打坏。
- 边缘函数不持有任何密钥，不做鉴权，只读请求 URL 与响应头。

## 9. 与 issue #63 的差异

| issue 原方案 | 本实现 | 原因 |
|---|---|---|
| KV 键 `namespace/school/grade/class` | `s1.<host>.<base64url(班级路径)>` | `/` 与非 ASCII 字符不被边缘 KV 接受 |
| 值 `version|time` | `{"v","e","g"}` | 需要多存一个世代字段；JSON 便于扩展 |
| PUT 后由源站返回新元信息、边缘 SET | 会改数据的方法（`PUT`/`POST`/`PATCH`/`DELETE`）成功后推进世代键 | 全局写入影响多个班级，边缘无法枚举键；也不需要改每个写接口。用白名单而不是「非 GET」是为了不把跨域预检 `OPTIONS` 也算成写 |
| 回源时拿新版本 | 回源原样透传，元信息由响应头带回 | 保留源站自己的 304 快路径，少一次源站请求 |
| 只考虑 `time` 兜底自动任务 | `expire = min(boundary, 下一个本地零点)` | 响应内容还随本地日期变化，跨天/跨周同样会失效 |
| 客户端不处理元数据 | 一致，客户端无需改动 | 客户端已经原样回传版本串 |

   而不是重新进入函数自身形成递归、也不是回到 Pages 项目。这是整个方案的前提，
   而我没有在真实环境验证过——详见 `docs/deploy.md` 第 3 节。

3. `new EdgeKV({ namespace: 'astra' })` 在函数运行时是全局可用的构造器。
4. ~~`s1.<host>.<base64url>` 形式的键能被 `put` 接受~~ —— **已实测通过**，见下。
5. 函数路由生效后，天气接口、`/web/*` 与其他接口的透传行为正常
   （SaaS 是 serverless 模式，WebSocket 本身返回 501）。
6. `esa.jsonc` 只写 `entry`、不写 `assets` 时，ESA 接受这个配置并把项目当作纯函数
   （而不是因为缺 `assets` 报错）。若被拒，退路是补一个空的静态资源目录。
